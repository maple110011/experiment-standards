# 验收标准：这套流程自身的对错判据（详版）

> 从 `SKILL.md` 下沉到这里（第 38 轮）。**SKILL.md 里只留一行的索引**，细节在这里。
> 为什么要下沉：SKILL.md 是**每次触发都进上下文**的那一层，它自己有预算；
> 而本 skill 立文治的就是"信息量超过人的带宽"——**skill 自己不该成为那个过载源**。
> 什么时候读本文件：**每轮收尾时**、或**新增/修改一条规则时**、或**要给别人做评审时**。
>
> 八条测试里，**前四条检验课题，后四条检验流程本身**（目的持久性 / 规则可执行性 /
> 报告可达性 / 测量可信性）——后四条是唯一"不看你做了什么、只看这套流程还转不转"的判据。
> **任一条不过，就地修，不要继续往下堆。**

## 1. 五分钟测试

只读摘要卡的头两行和最后两行，合上，然后能回答：(a) 发生了什么；(b) 下一步选什么。
做不到 → 这张卡失败，重写。
→ [cadence.md](./cadence.md) §1

**它的机械形式（第 35 轮补）**：一个产出包**必须收口到一个入口**，且入口
**把包里其余每个文件都点名**（人只读入口就知道包里有什么、哪些可以现在不读）：

```bash
python scripts/check_collab_artifacts.py --package <产出目录>
```

**工作区尺度同理，但只要求点名根目录的 `.md`**（产物文件归 `INDEX.md` 管）：

```bash
# 入口：点名根目录其余每份 .md + 一行「先读 <哪一份>」+ ≤120 行
python scripts/check_collab_artifacts.py --workspace-entry <工作区>/START-HERE.md
```

⚠️ **工作区也会得同一个病**（第 36 轮实测）：某个运行了几十轮的工作区根目录有
**6 份 `.md` 抢着当入口**（最长的 1482 行、最短的 62 行），而**没有任何东西规定先读哪个**
—— 一份巨长的"经验记录"和一个短章程平级摆着，人只会都不读。
这正是本 skill 立文那句话在**工作区尺度**的形态："我会逐渐丧失对内容的把握。"
⇒ 工作区必须有且只有一个入口（建议 `START-HERE.md`），它 ≤120 行、
点名其余每份根文档、并**明说先读哪一份**。

立此的实测原因：同一个"我已经跟不上了"的任务，**有 skill 的一臂交了 9 个文件**，
而它的摘要卡（自身字段全过）**只点名了 8 个其它文件中的 1 个** ——
于是"更完整"直接变成"接手更慢"。**盲评判者独立地说了同一件事**：
"把**结果过载**换成了**文档过载**… 这一步导航成本是纯损耗"。
⇒ 规则不是"少交文件"（台账对长期运营是资产），而是
**"入口必须收口"** —— 人只读入口，其余按需取。
→ [human-facing-output.md](./human-facing-output.md) §3.9

## 2. 台账"被用"测试

方法台账每 3 条结论里，至少 1 条要有"被用于"字段指向具体的协议块编号。
全是"被用于：无"的台账是装饰品，删掉重来。
→ [ledgers.md](./ledgers.md) §3

## 3. 噪声免疫测试

小于最小可检测效应的改进，是否被如实记成 `薄` 而没有被写成结论。
这一条检验的是 agent 有没有在替你管理你自己的期望。
→ [digest-card.md](./digest-card.md) §1

## 4. 理论入账测试

每做完 5 个协议块，理论台账里是否有至少 1 条 `成熟度 ≥ 可研究的问题` 的条目，
或有一处写明"为什么没有"。长期为空说明第 6 步的触发条件从未满足 ——
通常是证据还没到 `稳定`，或者七级梯子在第 2 级（机械排除）就没走完。
→ [theory-ladder.md](./theory-ladder.md)

## 5. 目的持久性测试

每轮结束时 `goal_guard.py` 是否退出 `0`。
若连续 3 块未推进 `method`、或连续 4 块未推进 `bridge`，它会 FAIL。
**这一条检验的是"人给的目的还在不在流程里"**，而不是"这一块做得好不好"。
它是唯一一个**按轮**而不是按块计数的测试。
→ [guard-criteria.md](./guard-criteria.md)（守卫到底查什么）
→ [goal-persistence.md](./goal-persistence.md)

## 6. 规则可执行性测试

每当本 skill **新增或修改一条"应当被执行"的规则**，检查它是否配齐四件套。
**这一条检验的是"规则本身有没有执行力"**，而不是"某个协议块做得好不好"。

| 问 | 答不出时的动作 |
|---|---|
| 字段在哪（模板里的哪个位置能承载它）？ | 先加字段，别急着写规则 |
| 哪个校验会报错？ | 去 `check_collab_artifacts.py` 加一段，并**先确认它会 FAIL** |
| 哪套 fixtures 覆盖它（**每条失败路径一个场景**）？ | 按失败路径数建场景，加一个"不应误报"的对照 |
| 哪个变异能证明 fixtures 有效（**每条路径一个**）？ | 去 `test_fixtures_mutation.py` 加，并确认 `--mutation-test` 会抓到 |
| **它的判定能被调用者消费吗**（退出码）？ | 给 `main()` 加返回码，并在 fixtures 里**同时**断言"好输入=0 / 坏输入≠0" |
| **它会不会花稀缺资源**（提交额度 / GPU / 预算）？ | 去协议块写 `稀缺资源:` + **`杠杆上界:`（最多能换来多少）**——答不出就是还没想清 |
| **花出去之前，那份要交的东西有没有被机械核对过**？ | 跑 `python scripts/check_submission.py --csv … --expect-pos …` |

**判据（机械可查）**：`python scripts/check_collab_artifacts.py --mutation-test` 退出 `0`
—— 它保证现有 fixtures 拦得住回归；但**新增规则是否配齐四件，仍需人工按上表逐栏确认**
（新增的规则不在现有变异里，机器无从知晓）。
→ [goal-persistence.md](./goal-persistence.md) §"fixtures 自检与变异测试"

> ⚠️ **最后一行是本 skill 里唯一"花出去就改不回来"的动作**（第 37 轮补）：
> 提交额度不可逆，而"包里到底是什么"此前**只靠一次临时自查**。
> 实测代价：我在写那个核对脚本时，顺手用一段 inline Python 读自己的 `result.csv`，
> **因为编码取错、列整体错位**，于是脚本报出"判 1 的片数 0"—— 一个**完全伪造的结论**。
> ⇒ **"我自己看一眼"不构成核对。** 花额度之前必须跑：
>
> ```bash
> python scripts/check_submission.py --csv <result.csv> --zip <result.zip> \
>     --expect-pos <k> --test-dir <官方测试集目录> \
>     --score-npz <分数文件> --score-key <键名>
> ```
>
> 它核对 8 件"传上去就改不回来"的事：表头可识别 / 行数 = 片数+1 / 判 1 的片数**恰好等于 k** /
> 取值 ⊆ {0,1} / 序号 1..N 连续 / 切片 ID 与官方测试集逐一对应 /
> zip 里的 csv 与磁盘**逐字节一致** / 被判 1 的片**正是分数最高的 k 片**。

## 7. 报告可达性测试

校验脚本报出的**失败**，在**没有人替它设环境变量**的情况下是否真的读得到？
这一条检验的是"**检查本身会不会崩**"。

立此测试的实测原因是**一次真实崩溃**：`--self-test` 读 fixtures 的中文输出时
`UnicodeDecodeError` → `r.stdout` 变 `None` → `AttributeError` → **整个自检带 traceback 死掉**；
同一天又撞上它的另一半：守卫 FAIL 提示里一个有 `⇒` 的字符在 cp936 控制台上印不出来，
于是**守卫在"报告失败"的那一行崩掉**。

**为什么它比"检查报 FAIL"严重得多**：报 FAIL 是一个能被读到的信号；
带 traceback 死掉**看起来像环境问题**，人会绕过它，于是那条检查静默失效。

**修法（已落成一条纪律）**：所有脚本的子进程调用与自身输出都走 `scripts/subproc.py`
（强制子进程 UTF-8；自身输出不可编码时降级为 `?` 而不是抛异常）。

⚠️ **它一度只覆盖了 skill 自己的脚本** —— 而**工作区里那些真正产出实验数据的脚本
没被覆盖**，偏偏它们跑得最久。实测代价：一个跑了 **327 秒**的扫描在最后
"打印报告"那一行崩掉，而结果写在报告**之后** ⇒ **整轮计算全丢，只能重跑**。
所以第 20 轮补了 `scripts/check_console_safe.py`（可对任意 `.py` 跑）
和一条**顺序纪律**：**结果先落盘，报告只是渲染**（见 `human-facing-output.md` §4）。

**判据**：三条命令都退出 `0` ——
`python scripts/subproc.py`、
`python scripts/check_console_safe.py`（lint 本 skill 全部脚本）、
`python scripts/check_console_safe.py <工作区里的脚本>`；
且 `test_suspension_fixtures.py` 的 `bare-console` 场景
（**故意不给编码环境变量**）仍能读出 FAIL。

## 8. 测量可信性测试

在给任何一轮评测（A/B、with_skill vs without_skill）打分**之前**，
先确认"**被打分的那些产出还在**"。这一条检验的是"**成绩单本身是不是可信**"。

立此测试的实测原因是**一份摆了十几轮的错成绩单**：成绩单上那条
"**skill 在核心题上毫无增益（+0.00）**"，题目恰好是"我已经跟不上了、很抗拒继续做"
—— 也就是本 skill 立文要治的症状。而真实原因是**我在那个 agent 还在写产出的时候
重构了目录**：一处 `outputs/` 空、一份被打分的残缺副本（完整副本就在隔壁）。
拿完整副本按同样断言重打 ⇒ **+0.40**。两条区分开 skill 与基线的断言
**恰好都是 skill 自带的构造**。

**为什么它必须独立成一条**：一般的 bug 让程序崩，这一类让**你把自己好的东西扔掉** ——
"skill 在这件事上没用"这个结论足以终止整个优化工作。

```bash
# grading 之前必跑；有 INVALID 就不许打分（退出码 1）
python scripts/check_run_integrity.py <工作区>/iteration-<N>
```

四条硬规则：
1. 评测开始后**不许移动/重命名任何被评测 run 的产出目录**，直到 grading 完成；
2. **空产出记 `INVALID`（重跑），绝不记 0 分** ——
   0 分是"做了但没做对"，空产出是"**这次测量没有发生**"；
3. 同一 run 两份**不一致**的产出副本 ⇒ `INVALID`，先确定哪一份是准的；
4. 看到 `delta ≈ 0` 先分三问（**两臂都接近满分？有臂没有产出？**），
   非区分型测试要改**断言**，测量事故要改**流程**，都不是才轮到"skill 真没帮上"。

**盲评（要"哪一版更好"的答案时）**：
```bash
python scripts/make_blind_pair.py --a <臂1> --b <臂2> \
    --out <盲评目录> --mapping <盲评目录之外>.json
```
去标识不是可选项（实测：对照臂的 `answer.md` 里写着自己的产出路径、含臂名，
原样交出去盲评当场失效）。且必须要求评判者**把内容分与结构分分开给** ——
否则你拿到的总分正是"形式"最容易污染的那个数。
→ [goal-persistence.md](./goal-persistence.md) §"测自己"

## 9. 提交可复现测试

**判据**：交出去的那份代码，按它自己 README 里写的那条命令跑一遍，
必须得到**与提交结果逐行相同**的结果；跑不出这条证据，就不许提交。

```bash
# 跑的那一半（要真数据）：按 README 原文跑、与提交结果逐行比，并留下记录
python scripts/check_package_repro.py --pkg <包.zip> --data-dir <测试数据目录> --write-record
# 静态的那一半（不要数据）：结构 / README 命令唯一 / 依赖带版本 / 记录是否过期
python scripts/check_submission.py --csv result.csv --expect-pos <k> --code-zip <包.zip>
```

**真实代价（第 41 轮，一次踩了三份，其中两份已经交出去了）**：

六份提交里三份的 README 命令复现不出它自己：一份交 **11** 个正类、复现成 **34** 个（差 23 行）；
一份交 **34** 个、复现出**另一组 34** 个（集合不同）；一份交 **150** 个、复现成 **34** 个（差 184 行）。
成因一律是**复制**：README 的运行命令是从另一个包复制来的，入口脚本的默认参数也是复制的；
其中一份的 README 甚至自己跟自己矛盾（页脚注释写的是本包真实参数，命令写的是上一个包的）。
按该课题的提交规范，"复现结果与提交结果不一致"是**取消资格**那一档。

**为什么它必须独立成一条**：这一层此前**只靠一次临时自查**，而"临时自查"恰恰是
本 skill 认定不构成核对的那种东西（`check_submission.py` 原先也只核 CSV 与 zip，
**从不打开代码包** —— 最不可逆的那类错，是唯一没被机械化的一类）。
更关键的是：那三份的入口脚本**静态看一条毛病都挑不出来**（它们自己的用法注释是对的），
所以这条测试只能由"真跑一遍"来承担，任何更严的静态检查都替代不了它。

**这条测试的三条设计选择**（都是踩出来的，别改回去）：

1. **跑的是 zip，不是解开的目录** —— 交上去的是压缩包；改了代码忘了重打包，等于没改；
2. **README 命令必须唯一** —— 给两条不同命令，复现者就不知道该跑哪条（上面那三份的原形）；
3. **比对用"逐行相同"而不是"分数差不多"** —— 提交的是 0/1 标签，差一行就是两份东西；
   行序无关（按 ID 列对齐），字节序不同不算问题；
4. **ID 列与判断列由调用方指定**（`--id-col` / `--label-col`），或由工具按
   "唯一取值 ⊆{0,1} 的列"自动识别 —— **skill 不认识任何课题的列名**（见 `check_genericity.py`）。

**不能机械化的那一半怎么办**：脚本替评审跑不了代码（它没有数据），
但可以要求**跑过的记录必须在**（`repro-check.json`）、**必须 PASS**、
**且与当前这份 csv 的 sha256 对得上** —— 改过 csv 忘了重跑，记录当场过期。
记录不能"证明"谁跑过，但它让"从没跑过"这件事**无法保持沉默**。
