# 目的持久性（治"跑着跑着就偏了"）

## 这条规则解决什么

多轮协作里，agent 会**静默地**偏离人给的目的。不是它故意，而是：

1. **人的目的往往是复合的** —— 解决实际问题 + 积累方法洞见 + 从实践里长出理论课题。
   这三者在每一步的"下一步该做什么"上会**给出不同的答案**；
2. **每个局部决定都看起来合理** —— "提高分数"本身就是一个合法决策，
   于是协议块的自检（"它改变哪个决策"）会**盖章通过**，即使它完全不推进另外两个目的；
3. **偏离没有参照物** —— 如果目的只存在于对话里，就没有任何东西可供对账。

### 一次真实的失效（这条规则的来源）

在一个真实会话里，agent：

- 连续两轮（约 6 次提交探测 + 特征与提交包工程）**完全投入竞赛工程**；
- 期间**方法学台账零更新**；
- 人不得不在中途打断并指出"我们的目标已经偏离了"。

**根因不是 agent 不听话，是这是三件事同时缺失：**

| 缺失 | 后果 |
|---|---|
| 没有 `CHARTER.md`（目标宣言从未落盘） | "偏离"没有参照物，只能靠记忆争论 |
| 台账条目不携带"推进哪个目的"的标记 | 无法机械统计"过去 N 块推进了什么" |
| 没有任何**运行时**检查 | 验收测试都是**事后**的（"理论入账测试"每 5 个块才查一次） |

**为什么必须是脚本**：把同样的话写进文档，在忙碌时一定会被跳过 —— 这次就是。
一个只在"有人维护它"时才起作用的纪律，等于没有。

## 机制：`scripts/goal_guard.py`

### 输入（四样，缺一样都会报出来）

1. **`CHARTER.md` 的 `<goals>` 块** —— 每行 `` - `tag`: 描述 ``。tag 是机读的，描述是给人读的。
   建议至少声明三个：`basis`（解决实际问题）、`method`（方法洞见）、`bridge`（从实践长理论）。2. **台账条目上的 `[tag]` 标记** —— 标题形如 `## M-3 [method] 主张……`。
   **不打标记的条目无法参与对账，会被列为 WARN。**
3. **协议块目录** —— 文件名里的编号定义"块顺序"。
4. **`DECISIONS.md`** —— 区分"agent 自己改了主意"与"用户决定的变更"。

### 输出与判定

- 每个目的的**条目数**与**最近一次推进之后又过了几个块**；
- **连续 N 块未推进某目的** ⇒ FAIL（默认：`method` 阈值 3、`bridge` 阈值 4）；
- 台账条目的 **mtime 陈旧度**（落后最新协议块多少天）⇒ WARN；
- **未打 tag** 的条目清单 ⇒ WARN；用了未声明 tag ⇒ FAIL；
- 退出码：`0` 无偏离 / `1` 有 WARN / `2` 有 FAIL（偏离已确认）。

### 用法

```bash
python scripts/goal_guard.py \
  --charter CHARTER.md \
  --ledgers ledgers/ \
  --protocols protocols/ runs/ \
  --decisions DECISIONS.md
```

**放在工作流的末尾（步骤 9），每轮结束跑一次。** 它的输出是人下一次开口前
唯一需要看的东西之一 —— 它不是汇报，是**报警器**。

## 目录约定（此前失效的地方）

本规则还固定了产物位置。此前一次会话里，skill 定义的约定
（`CHARTER.md`、`ledgers/`、`protocols/`）**从未生效**，agent 一路在 `iteration-3/` 下裸奔，
于是守卫把 75 份评测产物误当成台账条目。约定如下：

```
<workspace>/
  CHARTER.md                # 目标宣言（含 <goals> 机读块）
  DECISIONS.md              # 决策日志（人定的变更）
  MAP.md                    # 给人看的地图
  ledgers/
    problem-<topic>.md      # Q-*  [basis]
    methods-<topic>.md      # M-*  [method]
    theory-<topic>.md       # T-*  [method] 或 [bridge]
  protocols/
    PROTOCOL-<id>.md        # 一闸门一块
  runs/                     # L1 记录包（experiment-standards 的产物）
```

**`--ledgers` 必须指向 `ledgers/`，不要指向工作区根** —— 否则守卫会扫到历史版本的台账
与评测产物，报出一堆假条目。

### 工作区根必须**只在一处** —— 同名空目录会让工具静默返回"不存在"

**实测**：本仓库的工作区从仓库根搬进 skill 所在目录后，根上留下了一个**同名空壳**
（`collab-lab-workspace/`，里面只有一个空的 `literature/`）。
之后一次 `glob collab-lab-workspace/ledgers/*.md` **返回"没有文件"** ——
那不是"台账不存在"，是**工具解析到了空壳**。差一点据此得出"工作区为空"的结论。

**为什么危险**：这类失败**不报错、不给警告**，只给一个"零结果"，
而零结果与"真的没有"在输出上**长得一模一样**。

**约定**：
1. 工作区根路径在 `CHARTER.md` 顶部与每次调用的命令行里**各出现一次**，
   **不要靠"同名约定"去猜**；
2. 换工作区位置时，**顺手把旧路径清掉**（哪怕它是空的）—— 留着的空壳就是下一次的陷阱；
3. **零结果的正确反应不是"它不存在"，而是"我解析到的是哪一份"**：
   先确认那个路径下**确实有文件**（例如 `ledgers/` 非空），再下结论。
   `goal_guard.py` 对 `--charter` 不存在会直接 FAIL，所以**走守卫的调用是安全的**；
   危险的是**绕过守卫**直接读文件的那一步。

## 与其它机制的关系

| 机制 | 关系 |
|---|---|
| `CHARTER.md` | 是守卫的**唯一参照物**。没有它，守卫直接 FAIL 并拒绝继续 |
| 三级台账 | 条目的 `[tag]` 把"台账"与"目的"连起来。**没有 tag 的台账是装饰品** |
| 理论梯子 | 守卫管"有没有推进"，梯子管"推进得够不够深"。两者互补 |
| `DECISIONS.md` | 守卫据此判断某个"沉默"是用户决定的封存，还是 agent 的跑偏 |
| 验收标准里的"理论入账测试" | 那是**事后**检查（每 5 块）；守卫是**每轮**检查。缺了守卫，事后的那一条永远等不到触发 |

## 反过来：守卫**不能**做什么（避免把它当万能）

- 它**不判断**某个协议块的价值，只判断"这个目的有没有被推进"。一个低价值的块
  只要打了 tag 就能通过 —— **tag 打错比不打更糟**，因为它会制造"有推进"的假象。
- 它**不替代**人的判断。它只保证"偏离会被看见"，不保证"方向选得对"。
- 它**不处理**"目的是错的"这种情况。目的写错了要改 `CHARTER.md`，
  而改宣言必须由人点头（属于 `DECISIONS.md` 的范畴）。

## 守卫自身的**三**次修正（记在案，因为它们是"用出来的"）

### 修正一：`basis` 不参与 FAIL —— 一个真实假阳性

第一版对**所有**目的做偏离判定，结果在"补做追溯性文档"之后报出
「`basis` 最后入账后又有 6 个块」的 FAIL。**但那是假阳性**：
补做文档（补齐缺口、修好悬空引用）会让台账 mtime **晚于**所有旧块，
而那个"差距"衡量的是"块有多新"，不是"`basis` 被搁置"。

**修法**：只有 `method` / `bridge` 参与 FAIL —— 这两个才是会被工程挤掉的目的；
`basis` 的差距只作 `INFO` 报出供人判断。

### 修正二：把"事后补记"识别出来，而不是惩罚它

第二版加了一条反向识别：**若某目的的最新条目比最新协议块还新 ≥1 天**，
报 `INFO 追溯性入账` 并**不计入偏离判定**。

理由：惩罚"补做文档"会让人**不敢**补，而补文档恰恰是这套流程鼓励的行为。
**机制不能惩罚它想要的行为。**

### 修正三：区分"未开工 / 早期"与"偏离"（**同一个根因的两种表现**）

**触发方式**：本轮做了一次"干净场景端到端演练"——新建一个空工作区（只有 `CHARTER.md`），
跑守卫和一屏。演练立刻抓到两个误诊，**它们根因相同**：

| 表现 | 误诊 | 真相 |
|---|---|---|
| 空工作区（无协议块、无台账） | `FAIL 台账 没有找到条目` + `⇒ 已确认偏离`，退出码 2 | **还没开工 ≠ 走偏了** |
| 开工后只有 2 个块、`basis`/`bridge` 尚无台账 | `FAIL 目的 basis 声明了目的却零入账` | **早期本来就来不及每个目的都有入账** |

**为什么这是同一个根因**：守卫原来只有"偏离 / 正常"两态，
而实际有三态：**未开工 · 早期（还没到该有的量）· 偏离（该有的量没到）**。
**二元判定套在三态现实上，必然在早期误报。**

**修法**：
1. **未开工检测**（`detect_fresh_start`）：CHARTER 可解析 + 无协议块 + 无台账条目 + 无决策日志
   四条全满足 ⇒ 报"未开工"，退出码 **0**，并指出下一步该做工作流的哪一步。
2. **早期分级**：协议块数 `< 3` 时，"某目的零入账"记 **WARN**；`>= 3` 时才升 **FAIL**。
3. **回归验证**（必做，否则修完误诊可能把真偏离也放过）：
   晚期场景（8 块、`basis`/`bridge` 零入账）仍须 FAIL 退出码 2；
   已成热的课题仍须 `FAIL 0` 退出码 0。

**一般化**：**给"缺失"报警的机制，必须先区分"还没到时候"与"该有却没有"。**
否则它会在每个新项目一开始就给人一个假警报 —— 而假警报的代价是
**人从此不再相信这个报警器**，这比没有报警器更糟。

## 命名约定（机器靠它识别；**不遵守会静默失效**）

守卫用**文件名里的数字**取块号，正则是 `(\d{2,})` —— **至少两位数字**。

| 写法 | 会被识别吗 |
|---|---|
| `PROTOCOL-P-BOILER-009.md` | ✅ 块号 9 |
| `PROTOCOL-P-TEST-001.md` | ✅ 块号 1 |
| `PROTOCOL-P-1.md` | ❌ **不识别**（只有一位数字） |
| `block1.md` | ❌ |

**不遵守的后果是静默的**：守卫会报"没有找到协议块"，然后**跳过所有按块计时的判定**，
看起来"通过"，实际什么都没检查。
（写 fixtures 自检时我自己就踩了：用 `PROTOCOL-P-1.md` 造场景，
结果守卫一个块都没识别到 —— **这不是 bug，是命名约定的硬要求，此前只是没写下来**。）

## fixtures 自检与变异测试（**一次性验证等于没有验证**）

改守卫的行为时，必须有东西能拦住回归。为此有两层：

| 层 | 脚本 | 它防什么 |
|---|---|---|
| **守卫场景 fixtures** | `scripts/test_guard_fixtures.py` | 守卫行为改变：`fresh` 必须退出 0、`early` 必须 1、`drift` 必须 2、`clean` 必须 0 |
| **一屏场景 fixtures** | `scripts/test_status_fixtures.py` | `status.py` 的行为，**重点是它的解析没被破坏**（见下"解析器分裂"） |
| **证伪核对 fixtures** | `scripts/test_theory_staleness_fixtures.py` | "证伪条件待核对"这条检查的**比较方向**（`young` 不报 / `stale` 报，**只差 mtime**） |
| **第3档分流 fixtures** | `scripts/test_triage_fixtures.py` | 协议块的"第 3 档分流"校验：**三条失败路径各自隔离** + 一个"无第3档不应误报"的对照 |
| **变异测试** | `scripts/test_fixtures_mutation.py` | **fixtures 自己是摆设**：故意改坏被测对象（8 个变异），要求 fixtures 报 FAIL |

```bash
python scripts/check_collab_artifacts.py --self-test        # 含四套场景 fixtures
python scripts/check_collab_artifacts.py --mutation-test    # 对校验器的校验（改动任一脚本后跑）
```

**"三条失败路径各自隔离"是什么意思**（第3档分流那一套）：该检查有三条**独立**的失败路径 ——
① 有第3档行但缺分流节；② 有分流节但没标小类；③ 标了"可扫"却没写扫描范围。
**一个"合法 / 非法"两场景对只能证明"检查会响"，不能定位是哪条路径失效了。**
所以做 4 个场景，每个只改动分流那一处；额外加一个"无第3档 ⇒ 不应误报"的对照防止过严。
变异测试也为这 3 条路径各配一个变异（M6/M7/M8）。

**这四件套不是可选项**（见下 M-10）：规则要真正被执行，需要
`字段 + 校验 + fixtures + 变异测试`，**四件缺一它就会重新退化**。


**为什么"证伪核对"那一套要两个并排场景**：这条检查的全部逻辑就是一句
`if ledger_mt < max(ex_mtimes)` —— **正因为极简，它最容易被静默改坏**（比如有人把比较写反）。
并排的 `young` / `stale` 只差 mtime，**任何"恒真/恒假/写反"的改动都会让其中一个失败**；
**单场景做不到这点**（把比较恒真或恒假都能"通过"）。

**为什么需要变异测试这一层**：fixtures 自己也可能"只会说 OK"。本轮实测它**四次**失效：
块号不足两位导致一个块都没识别；`early` 场景因为补了 Q/A 台账而**没测到"零入账"那条路径**；
`status.py` 里被变异的那段解析是**死代码**；以及"证伪核对"最初没进基线/复原检查。
四处都是断言太松或覆盖漏项，不是代码错。
**只有"故意改坏它、看它叫不叫"才能证明一个自检有效。**

## 两条与"解析"有关的硬规则（都是本轮实测换来的）

### 规则一：两个脚本消费同一份文本时，解析器只能有一处定义

`status.py` 与 `goal_guard.py` 读同一批文件（CHARTER / 台账 / 协议块）。
`status.py` 曾经**自己复制**了一份 `BLOCK_THEORY_RE` 和 `BLOCK_GOAL_RE`。
守卫侧后来把正则从 `理论条目[:：]` 改成 `理论条目[:：|\]]`，**副本没同步** ——
而 `status.py` **照样跑、照样输出**，只是那一栏悄悄变空。

⇒ **修法**：正则与解析函数统一在 `goal_guard.py` 定义，`status.py` 导入；
`status.py` 里**不许**再写本地副本（本地副本会遮蔽导入的那份）。
变异测试用 `(?!)`（永不匹配）模拟这类失效，要求 fixtures 报 FAIL。

### 规则二：没被使用的解析是**死代码**，而死代码无法被测出回归

把"块 → 理论条目"的映射从一屏上移走后，`tm = BLOCK_THEORY_RE.search(t)` 的返回值
**没有任何地方再用**。此时变异测试 M4（让该正则永不匹配）**没能被 fixtures 拦住** ——
因为那一栏根本不显示，测试无从断言。

⇒ **修法**：要么删掉那段解析，要么**让它真的被用**。
本轮选了后者（把"理论链接："按块列出来）—— 因为块→理论的映射恰好回答了
"**为什么这么做**"，是人真正需要的那一栏。
**一般化：当变异测试"拦不住"某个改动时，先问那段代码是否真的还在起作用。**


**mtime 用 `os.utime` 显式设定，不用 `sleep`** —— 让场景确定、秒级完成。

## 仍然存在的已知局限（不打算修，只记录）

**把历史块追溯性补上 `[goal]` 标记，可以掩盖当时的静默。**
守卫无法区分"当时就打了标记"与"事后补的"。

⇒ 这是**已知局限，不是可修的 bug**。降低它的唯一办法是降低补标记的必要性 ——
**即一开始就别跳过闸门**。
