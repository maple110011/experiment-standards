# 探究地图与多 agent 汇总

> 这一层治的是一个比"信任"更前置的问题：**人没有内在地图。**
>
> 同步层（协议块 / 摘要卡 / 决策卡）解决"这一次实验说明了什么"。
> 它解决不了"**我到底走过了什么、下一步该往哪走**"——因为那些答案散在几十份
> 人没写过的文件里，人无从建立地形记忆。

## 1. 症状与成因

| 症状 | 说明 |
|---|---|
| 我说不出"已经试过哪些路线" | 知识全部存在于**非本人产出**的工件里 |
| 我对实验数据没有感觉 | 每个数字都是转述来的，没有一次亲手核对 |
| 我完全依赖 agent 的汇报 | 报告是唯一入口；报告漏了什么，我就永远不知道 |
| 我不知道往哪走 | 方向只能从"已走过的地形"里推，而地形是空格 |

**这不是注意力问题，是结构问题。** 让人"多读一点"无效——读得越多，未消化的
工件越多，抗拒越强。

## 2. 机制一：`QUESTION-MAP.md`（探究地图）

**唯一的组织原则：按信息增量分组，不按时间/文件/实验编号分组。**

一份地图把人需要判断的东西分成五节：

| 节 | 含义 | 使用方式 |
|---|---|---|
| **一、已确认** | ≥2 条独立来源一致 | 可以直接当作已知使用 |
| **二、有冲突** | 不同来源给出不同答案 | **使用前必须先看裁定** |
| **三、单来源** | 只有一次报告、未经复核 | **不得当已知**，要引用就先复核 |
| **四、已证伪** | 曾被报告、已被推翻 | 走过的弯路清单——最容易被重新提出，必须留着 |
| **五、未探究** | 问题已知、无人做过 | **新方向从这一节里选** |

每条必须带：**主张 / 独立来源强度 / 备注或裁定 / 来源**。

### 为什么第四节（已证伪）最重要

被推翻的结论有一种危险的复活能力：它们当初听起来合理，所以下一个人（或下一个
agent）很容易独立地重新提出同一个错误。**把证伪记录留在最显眼的位置，
是防止同一个坑踩两次的唯一廉价手段。**

本仓库的一次实测：8 条被证伪的结论里，有 5 条根因是同一个形状——
**数值没带定义**（"噪声下界 9 分"没说量名与 τ 依赖；"136 片"没说按列名还是按索引对齐；
"7 台设备"没说去重口径）。留下证伪记录才能看出这个模式；不留，就只会觉得
"怎么老出错"。

### 生成方式

不要让 agent 自由发挥去写地图。**用脚本跨产出目录扫描、聚合同一问题上的答案变体**，
再逐条裁定。自由发挥会产出又一份"汇报"，而不是地图。

可复用的做法（本仓库 `_conflict_scan.py` 即此实现）：

1. 列出"本轮被问过的问题"（从台账与协议块编号取，不靠回忆）；
2. 对每个问题，在**所有**产出目录里正则检索答案变体；
3. 变体数 > 1 的进第二节，= 1 且只有一条来源的进第三节；
4. 人工/agent 对每个冲突写裁定（是"不同的量"还是"真矛盾"）；
5. 第五节从"有人提过但没人做"的清单里取。

第 4 步是必须人工介入的地方：**多数冲突不是真矛盾，而是同一个词指不同的量。**
裁定要写清哪个量、什么口径、对哪些未知参数有依赖。

## 3. 机制二：`CONTRADICTIONS.md`（多 agent 冲突台账）

fan-out 只有在**汇总层**存在时才产生价值。N 个 agent 给出 N 份产出而不做比对，
等于把 N 份噪音堆给人。

冲突台账的字段：

```
### X-<序号> <一句话问题>
各方向答:  <方向 A: 答案+出处> / <方向 B: 答案+出处> / …
分歧类型:  真矛盾 | 同一个词指不同的量 | 口径不同 | 一方算错
裁定:      <结论 + 依据（哪个可复算）>
裁定依据:  <文件/命令>
该冲突暴露了什么: <流程缺陷，而不是"谁不认真">
```

**`该冲突暴露了什么` 这一栏是台账的价值所在。** 单条冲突只是麻烦；
十条冲突指向同一个流程缺陷时，那是**流程改进的入口**。

## 4. Fan-out 的硬纪律（做错了会得到"虚假共识"）

多方向试错确实有效——本仓库实测：同一份数据、同一个问题，不同 arm 给出
**6–9 种不同答案**，其中包含互相矛盾的机制解释。但价值只在满足以下五条时出现：

1. **方向必须真正不同。** 让 5 个 agent 做同一件事只会得到 5 份同质产出。
   方向应按**假设**分叉（"假设是数据问题 / 假设是方法问题 / 假设是评测问题"），
   不按参数网格分叉。
2. **先独立，后汇总。** 任何方向在给出自己的结论**之前**不得看到其它方向的结论。
   否则会发生锚定：后面的方向会向第一个方向靠拢，"不同"是假的。
   （本仓库一次实测：一个 without_skill 方向的 agent 主动报告"我读到了另一条的产出，
   我这条不再是干净对照"——**它做对了，但那条 run 必须作废**。）
3. **每个方向必须声明自己的答案会被什么推翻。** 写不出推翻条件的方向，
   它的产出无法进入裁定环节，等于白跑。
4. **禁止由发起者代写结论。** 汇总者可以裁定"哪个对"，不得把不同方向的结论
   糅成一段"综合结论"——那正是人无法核对的东西。
5. **必须记录"谁没找到什么"。** 一个方向报了"我没发现问题"也是有信息量的
   （说明那个方向不敏感），但**与"这个问题不存在"是两回事**。

### 危险：虚假共识

N 个方向异口同声，不等于对。同源模型的错误是**相关的**——它们会犯同一类错。
本仓库在一次评估里，两条独立 arm 都把同一个合成输入当成真实实验记录，
只是表述方式不同。**只有"来源真正独立"（不同数据、不同方法、不同提问方式）
才构成独立复核。** 同一模型跑两次不算。

因此地图里的"已确认"必须标注**独立来源强度**，不能只写"多方确认"。

## 5. 工具选择：用 DSH 现成的，不要先造系统

| 需求 | 用什么 | 说明 |
|---|---|---|
| 少量独立方向（2–4 个） | `subagent` / `subagent_fork` | 直接起，带独立 prompt |
| 大量方向、需要脚本编排 | `workflow` 工具 | fan-out + 各阶段，一条脚本跑完 |
| 长期存续的团队 | `.agent-teams`（实验性） | 有 `team.json` + `inbox/*.jsonl` 的船长制团队 |

**先不要为 fan-out 造专门的 agentteams 系统。** 本次实测的瓶颈不在协调，在验证：

- 本会话实测的并发上限是 **3 个会话（含调度者）**，
  16 个 run 因此跑了约 1.5 小时墙钟时间。**任何 fan-out 系统的实际吞吐都被
  这个上限卡住**，造系统不会让它变快。
- 真正的瓶颈是**汇总**：N 份产出需要有人比对、裁定、写进地图。
  这一层的成本远高于发起 fan-out。
- 因此正确的投资顺序是：**先把地图与冲突台账做好，再考虑扩大 fan-out 规模**。
  在汇总层不存在时扩大 fan-out，只会加速信息过载——那正是本 skill 要治的病。

### 什么时候才值得考虑专门系统

满足任一条时再说：

- 汇总层的成本已经成为瓶颈（地图与台账的维护跟不上产出的速度）；
- 需要**跨会话持久**的角色分工（这次是"数据勘察者"，下次还是它接手）；
- 需要不同的模型/算力配置承担不同方向（成本敏感的 fan-out）。

## 6. 失败模式

| 症状 | 诊断 | 修法 |
|---|---|---|
| 地图越来越长，没人看 | 按文件/时间组织而不是按信息增量 | 只保留五节结构；细节留在原产出里 |
| "已确认"节里全是同源复算 | 把"同一份数据的第二次计算"当独立来源 | 标注来源强度，同源只算 `薄` |
| 冲突节长期为空 | 要么方向太同质，要么没人比对 | 让方向按假设分叉；跑一次跨产出扫描 |
| 汇总成了一段"综合结论" | 汇总者代写了结论 | 改成"逐方向列答案 + 裁定哪个对" |
| fan-out 规模涨了但进展没涨 | 汇总层跟不上 | 停止扩大 fan-out，先修地图与台账 |
| 已证伪的结论又出现了 | 证伪记录没留在显眼处 | 地图第四节前置；引用前先检索 |
| 各方向结论高度一致就觉得稳 | 虚假共识（同源错误相关） | 检查来源是否真的独立 |
